**Document ID:** ADO-ARCH-001  
**Version:** 1.0  
**Status:** Initial Baseline  
**Architecture:** Cloud Control Plane + Distributed Execution Plane  
**Repository Strategy:** GitHub  
**Coding Engine:** OpenAI Codex SDK  
**Pilot Projects:** Fitbest / AI Development Organization

---

## 1. 项目目标

建设独立的 AI 数字化研发管理平台，支持多个软件项目、多种专业 Agent 和分布式开发执行环境。

平台需要实现：

1. 多项目统一管理。
2. 专业 Agent 注册、配置和调度。
3. 研发任务自动拆分和分配。
4. Codex SDK 代码开发执行。
5. 本地和远程 Worker 统一接入。
6. GitHub 仓库及 Pull Request 管理。
7. 自动测试、缺陷反馈和修复。
8. 人工审批和发布管理。
9. 研发知识和执行历史持久化。
10. 运行成本、执行质量和项目进度监控。

## 3. 总体架构

采用五层架构：

### Layer 1：Management Interface
- Next.js Web Dashboard
- 项目管理
- 研发指挥对话
- Agent 管理
- 任务管理
- 审批管理
- 执行监控

### Layer 2：Cloud Control Plane
- API Gateway
- Authentication / Authorization
- Project Service
- Repository Service
- Agent Registry
- Task Service
- Workflow Engine
- Agent Orchestrator
- Approval Service
- Worker Gateway
- Event Service

### Layer 3：Agent Execution Plane
- General LLM Agent Runtime
- OpenAI Agents SDK（适用时）
- Codex SDK Runtime
- Test Runtime
- Build Runtime
- Specialized Tools

### Layer 4：Distributed Worker
- Windows Worker
- Linux Worker
- Android Build Worker
- Test Worker

### Layer 5：Data Infrastructure
- PostgreSQL
- Redis / BullMQ
- S3-compatible Object Storage
- Project Knowledge Storage
- Audit Logs

## 4. 技术选型

| Category | Technology |
|---|---|
| Frontend | Next.js + React + TypeScript |
| Backend | NestJS + TypeScript |
| Agent Framework | OpenAI Agents SDK / Custom Orchestrator |
| Coding Runtime | OpenAI Codex SDK |
| Database | PostgreSQL |
| Queue | Redis + BullMQ |

技术选择原则：模块化单体优先，Worker 独立部署。避免第一期过早微服务化。

## 5. 部署架构

### Cloud Control Plane

运行：
- Web Dashboard
- API Server
- Agent Orchestrator
- Workflow Engine
- Worker Gateway
- PostgreSQL
- Redis
- Object Storage

### Local / Remote Execution Plane

运行：
- Worker Agent
- Codex SDK
- Git
- Docker
- Git Worktree
- Testing Tools

Worker 主动与云端建立经过认证的连接，不开放公网入站端口。

### 通信关系

1. Dashboard 通过 HTTPS 调用 API。
2. API 与 Orchestrator 通过内部服务通信。
3. Worker 通过 WSS 主动连接 Worker Gateway。
4. Worker 通过 HTTPS / Git 与 GitHub 通信。
5. Codex SDK 在 Worker 本地运行。
6. 执行事件通过 Worker Gateway 返回云端。

## 7. 研发工作流

CREATED → PLANNING → WAITING_APPROVAL → READY → QUEUED → RUNNING → TESTING → REVIEW → MERGED → COMPLETED

异常状态：
- BLOCKED
- FAILED
- TIMEOUT
- CANCELLED
- REJECTED
- RETRYING

所有状态变化必须写入 task_events。

## 8. 项目隔离

每个项目必须具有：
- 独立 Project ID。
- 独立 GitHub Repository Binding。
- 独立知识库命名空间。
- 独立执行工作目录。
- 独立项目配置。
- 独立模型配置引用。
- 独立权限范围。

共享内容仅限于经过批准的公司级规范、通用技能和公共工具。

## 9. 安全原则

- GitHub App 最小权限。
- Worker 使用短期认证凭证。
- 项目级授权。
- Docker 非 root 执行。
- 默认限制文件系统和网络访问。
- 不允许开发 Agent 直接操作生产环境。
- 主分支禁止 Agent 直接推送。
- 合并和生产发布必须人工批准。
- 所有敏感操作保留审计日志。

## 10. 非功能性要求

- 任务执行具有幂等性。
- Worker 离线能够检测。
- 任务能够暂停、取消和恢复。
- 执行事件可以持久化。
- 支持多 Worker 并发。
- 支持多项目隔离。
- 具备模型费用和任务耗时统计。
- 关键数据具有备份和恢复机制。

## 11. 架构边界

第一期不实现：
- Agent 完全自主修改生产系统。
- 无人工审批的正式发布。
- 完全自动化的复杂多项目架构重构。
- 全功能企业级多租户 SaaS。
- 复杂独立向量数据库集群。

## 12. 架构验收标准

1. 可以创建至少两个项目。
2. 两个项目可以绑定不同 GitHub 仓库。
3. 可以同时连接多个 Worker。
4. 云端可以分配不同项目的开发任务。
5. Codex 可以在独立工作区执行代码任务。
6. 执行事件可以实时返回。
7. 任务状态和执行结果可以持久化。
8. 能够创建 GitHub PR。
9. 支持人工审批。
10. 不同项目之间不存在未经授权的数据访问。

## 13. 关键待确认事项
